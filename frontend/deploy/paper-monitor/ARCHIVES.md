# Generated collector detail archives

The existing minute paper-session collector keeps its existing schedule and observation authority. `detail_archive.py` replaces deletion of old generated detail with lossless gzip archives. Install this helper beside `reader.py` before deploying the new reader and worker, and update the top-level `manifest.json["files"]` map with the actual hashes of `detail_archive.py`, `reader.py` and `worker.py` before starting the collector. Preserve unchanged entries; auxiliary release metadata does not update the enforced hash map.

Only `observation-*.json` under a dated session or that session's `evidence/` directory is eligible. A session must have a completed `final.json`, be older than seven days, differ from the currently collected session, and contain an observation whose modification time is older than seven days. Summaries, final findings, pointers, state, alerts, account databases, receipts, ledgers, checkpoints, immutable research evidence and retired shadow state are excluded.

Each archived detail has two retained files below its session's `archives/` directory: `{original relative path}.gz` and `{original relative path}.archive.json`. The v1 archive manifest records original path, byte count, original SHA-256 and compressed SHA-256. Publication uses temporary files, file/directory synchronization, compressed-byte verification and a source identity/size/modification check before unlinking the original generated detail. Interrupted work preserves readable source detail; readers reject a damaged or mismatched archive. There is no archive expiry/deletion policy.

Readers resolve source detail first, then verified archives, retaining the original publication's canonical checksum. Already-pruned legacy sessions can still use their retained final summary; missing old intermediate findings are omitted rather than fabricated. Finalization traverses one observation at a time, including archived evidence, preserving summary calculations without accumulating whole-day JSON records.

Each existing collector cycle archives at most 32 files, 8 MB of source detail, or about two seconds of work. A single file is limited to 2 MB; gzip level 1 limits CPU work. The existing collector service uses `Nice=10`, idle I/O scheduling and low CPU/I/O weights, allowing trading engines to take priority; its observation cadence/deadlines and prior memory/task limits remain unchanged. A batch is deferred when available RAM is below the greater of 128 MiB/15% of host RAM, swap usage reaches 75%, one-minute load exceeds 1.5 times CPU count, or storage reserve is insufficient. `archive-status.json` records deferral/failure without replacing a successful engine health observation. A batch failure never authorizes lifecycle or trading actions. Limits are per cycle, and a single small file can finish after the time budget boundary.

For isolated restoration, call `read_detail(session_folder, relative_observation_name)` and write the returned original bytes into a separate restore directory. Never restore an old archive over active collector/account state. The helper validates registered names and rejects symlink/path escapes; its archive reading limit is checked against the stored expected size. The main release owner verifies deployed helper hashes and old-session reads after installation.
