# Bounded state backup v2

`backup-state.py` preserves online SQLite backup semantics, including committed WAL records, and copies other files at their observed length. It does not make a transaction across every file; restore still requires native order/receipt reconciliation. It excludes lock files, WAL/SHM companions and symlinks. Active ledgers, order receipts, identity, interlocks and checkpoints remain in the backup.

The old 64 MiB source allowance could be consumed by the two 32 MiB executor journals alone. V2 admits at most 256 MiB of staged source, 10,000 files and 272 MiB of compressed archive. A single online SQLite copy has a 20-second deadline and checks the remaining byte budget during backup. Each staged file receives a size and SHA-256 entry in `snapshot-manifest.json` (`state-backup/2`). The new downloader verifies every member against that manifest, including source totals, before atomically publishing the local archive; it rejects links, traversal, duplicate members and oversized data.

`backup-remote.sh` runs the no-network, read-only-volume helper against private host-backed disk staging rather than the previous 128 MiB RAM tmpfs. It retains the 192 MiB helper memory ceiling, 256 MiB memory+swap ceiling, 0.25 CPU ceiling, dropped capabilities and low CPU priority. Preflight requires 944 MiB free host disk, covering the source allowance, packed archive, simultaneous stdout copy and reserve, plus the greater of 128 MiB/15% available RAM, swap below 75% and load below 1.5 times CPU count. Resource pressure defers work to a later timer; limits do not reserve or consume that much memory. Named helper containers are removed on timeout/exit before staging cleanup. Complete backups remain intact on failure.

The existing separate 28-generation backup rotation remains in place. No generated-detail archive deletion policy is introduced. The new source/transfer budgets are coordinated constants in the writer and local pull client; a budget failure must be investigated rather than raising limits indefinitely. Validate SQLite integrity and important account/order rows in an isolated restore before release.

Older v1 archives remain ordinary tar.gz files and remain manually restorable/inspectable in an isolated directory, with SQLite integrity checks and native reconciliation. They lack per-file SHA-256 attestations. The new pull client intentionally requires a fresh v2 latest archive; install the writer/script, create and verify a v2 backup, then enable the new pull client. Do not delete old backups or rewrite their manifests to make them appear attested. Rollback changes code/images, never newer account state or accepted-order receipts.
