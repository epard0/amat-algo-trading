## A concrete research-methodology improvement

The existing numerical evaluator already derives full-history, 2020-forward, 2023 and drawdown checks from source-bound native records. The controller’s older optional receipt path could nevertheless advance its research baseline from all-true receipt fields when an opt-in flag was enabled. The real campaign has kept that flag disabled throughout; this is not evidence that a running default was improperly changed.

The controller now rejects legacy boolean receipt promotion unconditionally, even if that flag is set in a fixture. Its baseline assignment has been removed. The historical prototype, tests and source are retained in the cycle’s source snapshot. No prospective enablement amendment was issued and the original sealed campaign protocol remains unchanged.

A new read-only bridge recomputes the numerical gates from five pinned bundles: candidate, current control, original anchor, native QQQ and independently accepted parent lineage. Each bundle contains all three costs, expected typed identities derived from frozen study/run inputs, exact record/protocol byte identities and a completed measurement manifest/receipt. The bridge checks profile, source, data, calendar, effective configuration, run/study, command arguments and record cost, then derives accepted-parent session hashes from the accepted lineage rather than accepting caller-supplied scalar reproduction claims.

The new CLI runs as an ordinary argv command under the existing bounded controller. It requires the active inherited run UUID, the actual campaign protocol/deadline/current parent, and frozen inputs for the policy, bridge and every current library source. Loaded research modules are attested before and after review. Reports can be created only in the active cycle directory with a safe label. Report and seal creation are exclusive and do not follow symlinks; partial evidence remains immutable and cannot be silently overwritten.

The JSON report is fsynced before its seal, so the pair is not an atomic transaction. Missing/partial seals fail closed and a failed attempt requires a new output identity. Tests cover that limitation explicitly.

## Trust limits are preserved

A report field claiming a trusted verifier source hash, or a hashed artifact that merely exists, does not prove the approved verifier actually ran or independently established the result. This bridge therefore accepts **no externally asserted nonnumeric validation reports**. All eight independent requirements remain unknown: causality, accounting, stress, forward validation, native planning, native execution, uncertainty and independent review.

Even a synthetic numerical winner can return only `pending_validation`; a numerical loser returns `rejected`. Every result has promotion and activation authority disabled and native profile verification false. A callback study’s parent v14.3 profile hash is not a deployable candidate profile. The bridge cannot update any baseline/default, grant broker capability or waive native parity. A future apply path still requires actual verifier producers, a prospectively reviewed protocol, a versioned native candidate profile, independent reproduction, coherent genuine default updates and an atomic baseline transition.

Pinned manifests, receipts and hashes establish recorded identity/provenance under the trusted coordinator. They are not cryptographic proof of scientific truth or untouched out-of-sample evidence. The original historical records and their source manifests are not rewritten to include the new verification code.
